## 1. Executive Overview

In automated, cloud-distributed media rendering pipelines, non-determinism is catastrophic. When rendering jobs run across heterogeneous execution nodes (e.g., local developer machines, ARM64 Apple Silicon instances, x86_64 AWS EC2 workers), any variation in system load, network latency, or scheduling can cause frame drops, audio-video desynchronization, and pixel variations.

Traditional browser-based automation tools (such as headless Chrome via Puppeteer or Playwright) rely on **wall-clock time** (`requestAnimationFrame`, system clocks). Under heavy CPU/GPU loads, dropped frames and timing jitter are inevitable.

The **Universal Video IR Rendering Engine** eliminates wall-clock time entirely. This document formalizes the architecture of **Deterministic Rendering and Deterministic Frame Capture**: guaranteeing that given the identical IR document and source assets, the engine produces **bit-identical, frame-locked media streams regardless of underlying hardware, compute load, or execution duration**.

│            │                                                           │

│   ┌────────────────────────────────────────────────────────────────┐   │
│   │              Discrete Frame-Stepping Loop (Frame t)            │   │
│   │                                                                │   │

## 3. Pillar 1: Discrete Frame-Step Scheduling (Zero Wall-Clock Dependency)

The runtime treats time not as an analog continuum, but as a discrete, ordered sequence of non-negative integers:

$$
t \in \{0, 1, 2, \dots, N-1\}, \quad \text{where } N = \text{totalFrames}
$$

### 3.1 Elimination of System Clocks

* **No Real-Time Throttling:** The rendering loop does not call `Date.now()`, `performance.now()`, `setTimeout`, or native timer interrupts to trigger frame redraws.
* **Variable Compute Cadence:** If Frame $t$ requires $1.2\text{ ms}$ to rasterize on an NVIDIA A100 GPU, and Frame $t+1$ requires $450\text{ ms}$ due to complex SkSL blur shaders on an overloaded CPU, the output timeline remains unaffected. Frame $t+1$ is never dropped, skipped, or interpolated against elapsed wall-clock time.
* **Monotonic Advancing:** The engine strictly advances the global playhead:

$$
t_{\text{next}} = t_{\text{current}} + 1
$$

Only after the rasterizer has flushed the completed frame buffer to the encoder consumer does $t_{\text{current}}$ increment.

## 4. Pillar 2: Seeded Procedural Generation & PRNG State Management

Organic video effects—including film grain, handheld camera shake, atmospheric dust, and lens jitter—frequently rely on random number generation. Unseeded operations (`Math.random()` or uninitialized C `rand()`) break determinism across runs.

### 4.1 Frame-Indexed Trigonometric Hashing

For fragment shaders executing inside Skia (SkSL) or Canvas pipelines, noise generation must be stateless, purely functional, and parameterized strictly by coordinate indices and the integer frame index $t$:

```glsl
// Deterministic 2D PRNG hash parameterized by frame integer t
float deterministicHash(vec2 uv, int frame) {
    float t = float(frame);
    vec2 p = uv + vec2(t * 0.1337, t * 0.7123);
    return fract(sin(dot(p, vec2(12.9898, 78.233))) * 43758.5453123);
}
```

Every pixel at coordinate $(x, y)$ on frame $t$ evaluates to the exact mathematical IEEE 754 floating-point value on every execution, guaranteeing identical visual static and halation.

### 4.2 Seeded Simplex / Perlin Gradient Grids

For procedural camera shake (`vfx/camera_shake`), the engine uses a seeded permutation table:

```typescript
export class DeterministicNoiseGenerator {
  private permutation: Uint8Array;

  constructor(seed: number) {
    this.permutation = this.generatePermutationTable(seed);
  }

  // Evaluates smooth continuous shake vector at exact frame index t
  public sample(frame: number, octave: number, frequency: number): number {
    const sampleCoord = (frame * frequency) + (octave * 100.0);
    return this.simplex1D(sampleCoord);
  }
}
```

* The IR schema accepts an optional `seed` parameter (defaulting to a deterministic hash of the sequence's unique string ID).
* Consecutive renders calculate the identical camera trajectory coordinates $(\Delta x, \Delta y, \Delta \theta)$ for all frames.

## 5. Pillar 3: Two-Pass Relational DAG Compilation & Temporal Immutability

Dynamic relational dependencies (`matchLengthOf`, `after`, `syncWith`, `paddingFrames`, `overlapFrames`) introduce potential race conditions if evaluated lazily during rendering.

### 5.1 Two-Pass Decoupling

```
[ Pass 1: Probing & Graph Ingestion ]
       │
       ▼
  Read Asset Stream Durations (libavformat headers, audio sample counts)
       │
       ▼
[ Topological Resolution (Kahn's DAG Algorithm) ]
       │
       ▼
  Resolve all relative constraints -> Immutable Frame Integer Map
       │
       ▼
[ Pass 2: Rendering & Rasterization ]
       │
       ▼
  Render purely against static integers: [startFrame, endFrame, durationFrames]
```

### 5.2 Resolution Proof

Given Sequence $B$ defined as:

$$
\text{Start}_B = \text{End}_A - \text{Overlap}, \quad \text{Duration}_B = \text{Duration}_{\text{Asset}} + \text{Padding}
$$

The two-pass compiler evaluates these equations **once** prior to frame allocation, writing an immutable `ResolvedTimeline`:

```typescript
interface ResolvedSequenceTimeline {
  readonly id: string;
  readonly startFrame: number;     // Absolute integer (e.g., 142)
  readonly endFrame: number;       // Absolute integer (e.g., 298)
  readonly durationFrames: number;  // Absolute integer (e.g., 156)
}
```

Because the render loop queries an immutable lookup table rather than evaluating live relational expressions, asynchronous race conditions between audio and video tracks are impossible.

## 6. Pillar 4: Deterministic Frame Capture & Synchronous Backpressure Handshake

To prevent buffer bloat and ensure zero frame drops, the rasterizer (Skia) and the multiplexer/encoder (FFmpeg/libavcodec) operate through a synchronous, backpressure-driven handshake.

```
┌────────────────────┐                     ┌────────────────────┐
│   Skia Rasterizer  │                     │   FFmpeg Encoder   │
│      (Producer)    │                     │     (Consumer)     │
└─────────┬──────────┘                     └─────────┬──────────┘
          │                                          │
          │ 1. Rasterize Frame t (Memory Buffer)     │
          │─────────────────────────────────────────►│
          │                                          │
          │ 2. Await Consumer Acknowledgment         │
          │    (Thread pauses / Async lock held)     │
          │                                          │ 3. Encode Frame t
          │                                          │    into AVFrame / Packet
          │                                          │
          │ 4. Buffer Consumption Ack / Ready Signal │
          │◄─────────────────────────────────────────│
          │                                          │
          │ 5. Increment t -> (t + 1)                │
          │    Begin Rasterizing Frame t + 1         │
          │                                          │
```

### 6.1 Handshake Implementation Modes

1. **In-Process Binding (libavcodec C++ / Rust FFI):**
   * The Skia rasterizer draws directly into an allocated `AVFrame` raw video buffer (e.g., `AV_PIX_FMT_RGBA` or converted `AV_PIX_FMT_YUV420P`).
   * The render thread synchronously invokes `avcodec_send_frame(codec_ctx, av_frame)`.
   * The frame counter advances only after `avcodec_receive_packet` returns `0` or `EAGAIN` (confirming consumption).

2. **Inter-Process Streaming (POSIX Pipes / Shared Memory):**
   * When piping raw pixel streams to an FFmpeg subprocess (`ffmpeg -f rawvideo -pix_fmt rgba -s 1920x1080 -r 30 -i pipe:0 ...`):
   * The engine writes exactly $\text{Width} \times \text{Height} \times 4$ bytes per frame into `stdin`.
   * The writer waits for the pipe write buffer to flush, preventing pipe buffer overflow and frame loss.

### 6.2 Zero-Copy Hardware Buffer Surface Transfers

For GPU-accelerated deployments:
* Surfaces are allocated via hardware handles:
  * **Linux:** `DMA-BUF` / EGL Image
  * **macOS:** `IOSurface` / Metal Texture
  * **NVIDIA:** `NVMM` / CUDA Surface Pointer
* The texture handle is bound directly to the hardware encoder (e.g., NVENC via `h264_nvenc` or VideoToolbox via `h264_videotoolbox`), eliminating CPU round-trip copies while preserving frame-lock synchronization.

## 7. Pillar 5: Audio Phase & Sample Clock Alignment

Video runs at frame rates (e.g., $24, 29.97, 30, 60\text{ fps}$), while audio runs at sample frequencies (e.g., $44,100\text{ Hz}, 48,000\text{ Hz}$). Fractional samples per frame introduce rounding drift over long timelines if handled naively.

### 7.1 Exact Sample Rate Math

At $30\text{ fps}$ and $48,000\text{ Hz}$:

$$
\text{SamplesPerFrame} = \frac{48000}{30} = 1600 \text{ samples (exact integer)}
$$

At non-integer frame rates (e.g., $29.97\text{ fps}$ / NTSC standard):

$$
\text{SamplesPerFrame} = \frac{48000 \times 1001}{30000} \approx 1601.6 \text{ samples}
$$

### 7.2 Bresenham Sample Accumulator

To prevent phase drift and truncation error, the audio DSP compiler uses an integer accumulator:

```typescript
export class DeterministicAudioClock {
  private accumulatedFraction: number = 0;

  public getAudioBoundsForFrame(frameIndex: number, sampleRate: number, fps: number): { startSample: number; sampleCount: number } {
    const exactStartSample = Math.round((frameIndex * sampleRate) / fps);
    const exactEndSample = Math.round(((frameIndex + 1) * sampleRate) / fps);
    
    return {
      startSample: exactStartSample,
      sampleCount: exactEndSample - exactStartSample
    };
  }
}
```

This guarantees that over a 2-hour timeline, the aggregated audio sample count matches the total frame duration down to the individual audio sample ($1/48000\text{th of a second}$), eliminating audio-video drift.

## 8. Verification & Testability Standards

To ensure cross-platform determinism across releases, the engine execution pipeline incorporates automated Bit-Identical Regression Testing.

### 8.1 Perceptual & Cryptographic Verification Pipeline

```
[ Output Video Stream (.mp4) ]
             │
             ├─────────────────────────────────────────────────┐
             ▼                                                 ▼
   [ Stream Demuxer ]                                [ libavcodec Decode ]
             │                                                 │
             ▼                                                 ▼
   Verify Container Atoms                            Extract Raw RGBA Buffers
   - Exact packet PTS/DTS match                      (Frame 0, Frame 1, ... Frame N)
   - Zero missing frame headers                                │
                                                               ▼
                                                     Per-Frame SHA-256 Hash
                                                     sha256(RawPixels_t) == Baseline_t
```

### 8.2 Hash Verification Suite

1. **Frame-Level SHA-256 Checksums:**
   * In software rasterization mode (`Skia CPU / llvmpipe`), every rendered raw frame buffer is passed to a SHA-256 hash accumulator:
   
   $$
   H_{\text{run}} = \text{SHA256}\left(\bigoplus_{t=0}^{N-1} \text{FrameBuffer}(t)\right)
   $$

   * Any divergence in a single pixel on any frame immediately fails the test pipeline.

2. **Floating-Point Consistency across Platforms:**
   * All color transforms, matrix operations, and easing equations strictly adhere to standard IEEE 754 floating-point operations.
   * Shaders enforce explicit float precision (`precision highp float;`) to prevent precision truncation differences between NVIDIA, AMD, Intel, and Apple GPUs.
