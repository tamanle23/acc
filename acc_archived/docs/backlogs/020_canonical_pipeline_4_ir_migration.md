## 1. Context & Problem
Currently, `StoryOrchestratedRenderStage` maintains a split code path: it only uses the Universal Video IR engine when `ctx.metadata?.useIRBackend` is explicitly set, falling back to `VideoEditPipelineOrchestrator.renderStoryVideo` (which renders scenes to individual temporary disk MP4 files, temporary ASS subtitle files, and joins them with ad-hoc FFmpeg filtergraph strings).

To achieve enterprise-grade reliability and performance, we must complete Option 2:
1. Promote the Universal Video IR engine (`IRChunkWorkerPool` / `IRMasterRenderer`) to be the **default, canonical rendering backend** for Pipeline 4 (`GenerativeStoryPipeline`).
2. Eliminate intermediate disk files (`scene_0.mp4`, etc.) and ad-hoc filtergraph string concatenation.
3. Preserve backward compatibility by turning `VideoEditPipelineOrchestrator.renderStoryVideo` into a thin facade over the canonical IR pipeline.
4. Verify the 8-point synchronization protocol (`STORY-CONFIG-8POINT-SYNC`).

---

## 2. Proposed Design
1. **Canonical IR Rendering in `StoryOrchestratedRenderStage`**:
   - Make IR rendering the default execution path in `StoryOrchestratedRenderStage`.
   - Leverage `IRChunkWorkerPool` with auto-detected hardware concurrency (`concurrency: os.cpus().length` or user-specified).
2. **Backward Compatibility Facade**:
   - Refactor `VideoEditPipelineOrchestrator.renderStoryVideo(...)` to adapt incoming `ResolvedStoryConfig` into a `VideoIRDocument` and render via `IRChunkWorkerPool`, ensuring any legacy callers benefit from the zero-copy, multi-worker parallel chunking engine.
3. **Automated Verification**:
   - Test standard Pipeline 4 execution via `bun test autogenerated-tests/canonical_pipeline_4_ir.test.ts`.
   - Ensure 0 regressions across existing test suites.
