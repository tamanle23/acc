# 403. Backend Sandbox Decoupling & Self-Contained Schema Initialization

## 1. Problem Statement
The backend development sandbox (`pnpm dev:sandbox`) executes the Spring Modulith stack (`acc-ms-aio`) with in-process PostgreSQL 17 WebAssembly (`io.roastedroot:pglite4j-jdbc`). During startup, core production components like `AuditPartitionProvisioner` in `acc-fw` attempt to ensure monthly partitions on `UNIPOST_RECORD_AUDIT_LOG`. 

An architectural boundary invariant was violated when sandbox-specific bypass code was temporarily added directly to `AuditPartitionProvisioner.java` in core `acc-fw`. Core business modules must remain 100% independent of sandbox mechanisms. All sandbox-specific accommodations, schema initializations, and snapshot lifecycle handling must live exclusively inside the `com.acc.sandbox` package in `acc-sandbox`.

## 2. Plan & Architecture
1. **Pristine Core Decoupling**:
   - Revert `apps/backend/acc-fw/src/main/java/com/acc/service/AuditPartitionProvisioner.java` to its original clean state with zero references or dependencies on `application.sandbox`.
2. **Self-Contained Sandbox Schema Initializer**:
   - In `PgLiteDatasourceConfiguration.java` (`apps/backend/acc-sandbox`), pre-provision the base partitioned table `UNIPOST_RECORD_AUDIT_LOG` and its default partition directly on the PGlite DataSource upon creation.
   - When downstream core beans (like `AuditPartitionProvisioner`) run their `@PostConstruct`, the partition DDL executes cleanly against the existing table in PGlite with zero errors or bypasses.
3. **Defensive Snapshot Integrity**:
   - In both `PgLiteDatasourceConfiguration.java` and `SandboxEnvironmentPostProcessor.java`, guard against empty or truncated files (`length() < 100`) from previous interrupted boots, purging invalid snapshots so PGlite always boots clean.
4. **Formal Verification Parity**:
   - Update `autogenerated-tests/backend_sandbox_safeguards.test.ts` to enforce that `acc-fw` has zero sandbox coupling.
