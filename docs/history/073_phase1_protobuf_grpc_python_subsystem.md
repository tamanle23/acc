# History Entry 073: Phase 1 - Protobuf Contracts & Python gRPC Backend Integration

## Problem Statement
The ACC system previously invoked Python workers on an ad-hoc basis over line-buffered `stdio` JSON. This approach incurred JSON serialization overhead for large payloads (masks, audio arrays, tensors), lacked strict typed contracts between TypeScript and Python, and risked process spawning bottlenecks on Windows. To support high-performance AI engines (Kokoro-82M, Depth Anything v2, MobileSAM, and local JSON grammar LLMs), a strongly typed, zero-churn gRPC communication subsystem was required.

## Plan
1. Create `packages/proto` defining typed Protocol Buffer contracts (`common.proto`, `tts.proto`, `vision.proto`, `llm.proto`).
2. Implement dynamic protobuf loader and typed RPC client factory in `packages/proto/src/index.ts` using `@grpc/proto-loader` and `@grpc/grpc-js`.
3. Create `apps/python-backend` managed via `uv`, generating Python gRPC stubs via `grpc_tools.protoc`.
4. Implement `apps/python-backend/src/server.py` supporting `TTSService`, `VisionService`, and `LLMService` over TCP `127.0.0.1:50051`.
5. Implement `IPCFacade` and `GRPCAIStrategy` with **Auto-Bootstrapping**: If the Python daemon is offline, Bun automatically bootstraps it in the background via `bun x uv run python src/server.py` and waits for health-check readiness (<1.5s).
6. Implement `FallbackAIStrategy` to guarantee zero-crash resilience if the Python backend is unavailable.
7. Write formal `bun:test` suite `autogenerated-tests/grpc_ipc_bridge.test.ts` to verify auto-bootstrap, multi-service ping-pong, and strategy switching.
