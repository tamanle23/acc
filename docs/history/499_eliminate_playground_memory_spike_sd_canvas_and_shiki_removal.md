# 499: Eliminate Playground Memory Spike with SD Quality Canvas and Complete Shiki Removal

## Problem Statement
When `@acc/studio` opened `IrPluginPlaygroundModal`, the JavaScript heap spiked past **$> 500\text{ MB}$** before gradually declining. Forensic memory profiling revealed:
1. **Unbounded High-DPI Canvas Backing Store**: Physical canvas resolution was calculated as `targetWidth * dpr`, reaching $2200 \times 1240$ on Retina / 2x DPR displays. In `CanvasScratchPool`, dimensions exceeding 1080p were escalated to the **4K Tier** ($3840\times 2160 = 33.2\text{ MB}$ per scratch canvas).
2. **1.32 GB/sec `getImageData` Allocation Firehose**: Default plugin `overlay/canvas_particles` with preset `cyber_sparks` ran dual `getImageData()` passes per frame at 60 FPS ($22\text{ MB}$/frame), allocating $654\text{ MB}$ of short-lived `Uint8ClampedArray` buffers in the first 500ms.
3. **Synchronous 5-Keyframe Storyboard Burst**: On modal mount, all 5 keyframes were computed simultaneously in a single loop.
4. **Heavy Shiki Syntax Highlighter Overhead**: `shiki` loaded TextMate grammars and Oniguruma/JavaScript regex engines, retaining $15\text{–}25\text{ MB}$ of AST heap.

## Plan & Architecture
1. Lock playground physical canvas backing store to **Standard Definition (SD Quality $\le 640\times 360$)**, with CSS GPU bilinear scaling to fill the stage. Prevents 4K tier escalation and caps canvas memory at $< 921\text{ KB}$.
2. Downsample bloom extraction in `PostProcessingShaders.applyBloom()` to a fixed $160\times 90$ scratch buffer ($57.6\text{ KB}$), achieving a $190\times$ reduction in post-processing buffer memory while enhancing diffuse glow aesthetics.
3. Stagger storyboard filmstrip keyframe rendering across `requestAnimationFrame` ticks (1 keyframe per tick) to eliminate mount burst contention.
4. Completely eliminate `shiki` from the project. Replace with an ultra-lightweight, zero-dependency, synchronous regex-based JSON tokenizer (`jsonTokenizer.ts` and `JsonCodeViewer.tsx`).
