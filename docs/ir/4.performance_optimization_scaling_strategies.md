# Technical Specification: Rendering Engine Performance & Scale
**Target Specification:** Video IR Runtime Engine (V1.0-Stable)
**Classification:** Performance, Concurrency, and Hardware Optimization

---

## 1. Executive Summary

While the **Universal Video IR Rendering Engine** guarantees determinism via discrete time discretization, rendering complex 4K compositions, Skia shader effects, and Lottie animations is computationally expensive. 

Because the IR engine pre-compiles a static Directed Acyclic Graph (DAG) containing absolute frame indices, the runtime possesses **perfect foresight**. It knows exactly which assets are needed, what pixels are visible, and when effects trigger before the first pixel is drawn. This specification details five core optimization pillars to achieve real-time or faster-than-real-time ($>30\text{ fps}$) rendering.

---

## 2. Pillar 1: Temporal Chunking & Distributed Rendering

Since time is treated as an absolute integer sequence ($t \in \{0, 1, \dots, N-1\}$), the rendering pipeline does not need to execute sequentially on a single machine.

### 2.1 GOP-Aligned Distributed Workers
A 10-minute video ($18,000$ frames at $30\text{ fps}$) can be distributed across 10 serverless worker nodes (e.g., AWS EC2 or Lambda).
* **Worker 1:** Renders Frames $0 \to 1799$
* **Worker 2:** Renders Frames $1800 \to 3599$
* ...and so on.

Because all procedural noise (camera shake, film grain) is parameterized by the absolute frame integer $t$, **Chunk 2 perfectly aligns with Chunk 1** with zero visual seams or PRNG jitter.

### 2.2 The "Padding" Solution for Temporal VFX
Effects like convolution reverb, motion blur, and crossfades require historical or future data. If Worker 2 starts at Frame 1800, it cannot compute a 10-frame crossfade that began at Frame 1795.
* **The Fix:** The orchestration layer instructs workers to render with a **Temporal Bleed Padding** (e.g., $\pm 30$ frames).
* Worker 2 actually processes Frames $1770 \to 3629$ in memory, but only flushes Frames $1800 \to 3599$ to the multiplexer.
* Finally, the engine uses FFmpeg's `concat` demuxer on GOP-boundaries (Group of Pictures) to seamlessly stitch the 10 MP4 chunks together losslessly in under 2 seconds.

## 3. Pillar 2: Zero-Copy Hardware Pipelining

In software-based renderers, transferring a raw uncompressed 4K frame ($3840 \times 2160 \times 4\text{ bytes} \approx 33\text{ MB}$) between the CPU memory (decoding), GPU memory (Skia rendering), and back to CPU memory (encoding) at 60 FPS creates a massive PCIe bus bottleneck ($>5\text{ GB/s}$).

### 3.1 Hardware Surface Sharing
The engine must utilize native graphics APIs (Vulkan, Metal, EGL) to share pointers rather than copying byte arrays.

```
[ Hardware Decoder (NVDEC / VideoToolbox) ]
       │
       ▼ (Passes GPU Memory Pointer)
       │
[ Skia / GPU Canvas Rasterizer ]
       │
       ▼ (Passes GPU Memory Pointer via DMA-BUF / IOSurface)
       │
[ Hardware Encoder (NVENC / VideoToolbox) ]
```

* **Linux (NVIDIA/AMD):** Assets are decoded to `AV_PIX_FMT_DRM_PRIME` surfaces. Skia wraps these in `EGLImage` textures. The composited output is sent directly to NVENC via CUDA interop.
* **macOS (Apple Silicon):** Frames are decoded into `CVPixelBuffer` backed by `IOSurface`. Skia (via Metal) draws directly onto this surface, which is passed synchronously to VideoToolbox for HEVC encoding. System RAM is completely bypassed.

## 4. Pillar 3: Occlusion Culling & Lazy I/O

Because the DAG knows the spatial and temporal layout of every sequence, the engine can intelligently skip rendering unseen pixels.

### 4.1 Temporal Occlusion Culling
If Track V2 contains a fullscreen, 100% opaque Sequence (e.g., a solid color graphic or fullscreen video) from Frames $500 \to 1000$, Track V1 is completely occluded.
* **Action:** The DAG compiler dynamically flags Track V1's asset decoder to pause decoding from $500 \to 1000$, saving massive CPU/GPU cycles.

### 4.2 Network-Level Byte-Range Ingestion
If an IR asset declares `"sourceTrim": { "startFrame": 3000, "durationFrames": 150 }`, the engine should **never** download the entire source file.
* **Action:** Using FFmpeg's HTTP seek capabilities or AWS S3 byte-range requests, the prober calculates the exact byte offset of the keyframe preceding Frame 3000. It streams only the required 5 seconds of network data, reducing a 10GB S3 transfer to a 15MB transfer.

## 5. Pillar 4: Spatial & Asset Memoization

Certain modifiers and data bindings result in visually static buffers over a long duration. 

### 5.1 Skia Picture Recording (Display Lists)
If a `news_ticker_graphic` composition (containing a bounding box, text, and logos) only changes its data payload every 300 frames:
* The engine does not issue hundreds of Canvas 2D calls (`fillRect`, `fillText`) every single frame.
* Instead, Skia records the drawing commands into an immutable `SkPicture` (Display List). 
* For the next 299 frames, the engine simply executes a high-speed blit of the cached `SkPicture` onto the master canvas, collapsing rasterization time from $2.5\text{ ms}$ to $0.05\text{ ms}$.

### 5.2 Lottie Frame Caching
Skottie evaluates vector math (bezier curves, trim paths) efficiently, but rasterizing complex particle effects is heavy. 
* If a Lottie animation sequence loops, the engine rasterizes the loop once into a GPU texture atlas. Subsequent loops simply sample the cached textures.

---

## 6. Pillar 5: Decoupled Asynchronous Audio Mixing

Video rendering requires GPU hardware, while audio DSP (Digital Signal Processing) requires precise CPU floating-point math.

* **Action:** The engine completely decouples the audio DAG from the video DAG.
* While the GPU is heavily loaded rendering visual frames, a lightweight thread compiles the entire audio mix (Tracks + Effects + Buses -> Master Bus) into a single, contiguous `.wav` payload asynchronously.
* Because audio processing operates thousands of times faster than real-time ($>100\times$), the master audio track is usually finished within milliseconds.
* The FFmpeg multiplexer then consumes the finished audio stream seamlessly as the video frames arrive, ensuring perfectly interlaced audio/video packets without blocking the video thread.

## 7. Performance Targets & Benchmarks

By implementing these optimizations, the Node.js/Rust bridging engine targets the following performance characteristics on standard cloud infrastructure (e.g., AWS `g4dn.xlarge` / NVIDIA T4):

| Workload Type | Resolution | NLE Approach | IR Engine Target | Optimization Pillar Responsible |
| :--- | :--- | :--- | :--- | :--- |
| Simple Concat (No VFX) | 1080p | 1.0x Real-time | **>15.0x Real-time** | Lazy I/O, Stream Copy (Avoid Decode) |
| Lottie + Video Overlay | 1080p | 0.5x Real-time | **> 3.0x Real-time** | Skottie Caching, Zero-Copy GPU |
| Complex Color LUT + VFX | 4K (UHD)| 0.2x Real-time | **> 1.0x Real-time** | Zero-Copy Hardware Pipelining |
| 10-Minute Timeline | 1080p | 10 Minutes | **< 60 Seconds** | Temporal Chunking (Distributed GOP) |

By treating video generation as a pre-compiled, mathematical operation rather than a live-playback emulation, the Video IR engine achieves enterprise-scale throughput suitable for massive AI-generation pipelines.
