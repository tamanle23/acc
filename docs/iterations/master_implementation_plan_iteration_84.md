# Master Implementation Plan - Iteration 84: Sidecar Worker Single Warmup Dispatch & Passive Barrier Architecture

## 1. Executive Summary
During studio bootstrap, `"Sidecar worker successfully warmed up."` was logged twice in the browser console due to dual-dispatch between `scheduleWarmup()` and `StudioBootController.waitForEngineWarmup()` (`warmup()`). Following the `/grill-me` alignment, the responsibility for initiating worker warmup is consolidated strictly into `initWorker()` upon worker creation, removing `scheduleWarmup()` and removing `this.warmup()` from `waitForWarmup()`. `waitForWarmup()` becomes a purely passive Promise barrier. Furthermore, per user directive, no silent drops are introduced into `handleWorkerMessage`; any unexpected duplicate response emits a visible `Logger.warn`.

---

## 2. Trade-Off Matrices
| Architectural Decision | Option A (Rejected) | Option B (Adopted) | Rationale |
| :--- | :--- | :--- | :--- |
| **Warmup Trigger Responsibility** | Boot-driven (`waitForWarmup` calls `warmup()`) | Worker-driven (`initWorker()` calls `warmup()`; `waitForWarmup()` purely passive) | Selected by user in `/grill-me`. Worker self-initializes immediately upon instantiation; splash screen passively waits for readiness. |
| **Background Scheduling** | Retain `requestIdleCallback` with timer cancel | Delete `scheduleWarmup` completely | Eliminates all timer races, microtask delays, and complex handle cancellations. |
| **Duplicate Message Handling** | Silent early return (`if (this.isWarmedUp) return;`) | Explicit `Logger.warn` without silent suppression | User mandate: unexpected duplicate responses indicate underlying bugs and must remain visible. |
| **Bridge Listener Lifecycle** | Retained unsubscribe cleanup | Keep as-is singleton attachment | Selected by user in `/grill-me`. Single process-level instance binds once. |

## 4. Mathematical & Algorithmic Specifications
Let $D$ denote the set of warmup dispatches:
$$|D| = 1$$

State tuple: $S = (W_{\text{done}}, W_{\text{active}})$
- $W_{\text{done}} \in \{0, 1\}$ (`isWarmedUp`)
- $W_{\text{active}} \in \{0, 1\}$ (`isWarmingUp`)

**Transitions**:
1. $\text{initWorker}():$
   $$\text{warmup}()$$
2. $\text{warmup}():$
   $$\text{If } W_{\text{done}} = 1 \lor W_{\text{active}} = 1 \implies \text{noop}$$
   $$\text{Else } W_{\text{active}} \leftarrow 1, \; \text{postMessage}(\text{WARMUP})$$
3. $\text{waitForWarmup}():$
   $$\text{If } W_{\text{done}} = 1 \implies \text{resolve}(true)$$
   $$\text{Else } \text{register}(\text{resolver})$$
4. $\text{handle}(\text{WARMED\_UP}):$
   $$\text{alreadyWarmed} \leftarrow W_{\text{done}}$$
   $$W_{\text{active}} \leftarrow 0, \; W_{\text{done}} \leftarrow 1$$
   $$\text{If } \text{alreadyWarmed} = 1 \implies \text{Logger.warn}("Duplicate WARMED\_UP response")$$
   $$\text{Else } \text{Logger.info}("Sidecar worker successfully warmed up.")$$
   $$\text{notifyResolvers}(true)$$

## 8. Risk & Rollback Mitigations
- **Risk**: In environments where worker creation fails, `waitForWarmup` might hang.
  - *Mitigation*: `waitForWarmup` retains its `timeoutMs` fallback and immediately checks `if (!this.worker) return Promise.resolve(true);`.
- **Rollback**: Revert `PreviewWorkerCoordinator.ts` edits to commit `ca17e281`.
